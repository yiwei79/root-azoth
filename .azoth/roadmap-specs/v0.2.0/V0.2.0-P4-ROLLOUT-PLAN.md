# v0.2.0-p4 Stabilization And Rollout Plan

Status: active milestone plan
Created: 2026-04-28
Roadmap version: v0.2.0-p4
Policy: freeze new initiative expansion until this phase closes

## Purpose

v0.2.0-p4 exists to turn the current Azoth work into something safe to use for
real projects. The phase is not a feature-growth phase. It is a stabilization,
release, and deployment-boundary phase.

The guiding decision is the hybrid operating model:

1. `root-azoth` remains the private development workshop and source of truth for
   toolkit evolution.
2. `azoth` becomes the clean public product repo produced by mechanical extraction.
3. The operator personal root becomes an installed Azoth deployment for personal
   project control, knowledge, and cross-project operation.

## Current Read

Autonomous-auto is complete for the shipped INI-AUTO-001 campaign, but the whole
repo is not release-clean yet. The release phase must preserve this distinction:

- Campaign truth: the autonomous loop can be Green and closed.
- Repo truth: generated mirrors, roadmap drift, installer versioning, product
  extraction, publish flow, and personal deployment still need release gates.

## Freeze Rules

- Do not schedule new initiatives during v0.2.0-p4.
- Do not add new autonomy, memory, planning-bank, platform, or product feature
  work unless a release gate fails and the repair is the narrowest safe blocker fix.
- Keep new ideas in proposals, initiative banks, or inbox evidence until p4 closes.
- Prefer validation, packaging, publishing, documentation, and deployment-boundary work.
- Keep public product defaults smaller than root-azoth's development control plane.

## Three-Plane Model

| Plane | Repo / home | Purpose | Owns | Must not own |

| Development workshop | `root-azoth` | Build, test, and govern Azoth itself | Source skills, agents, commands, roadmap, tests, extraction logic, release plans | Personal global KB as primary operating state, public consumer runtime state |

## CI/CD Rollout

### Root Validation

Root validation proves the development workshop is internally coherent:

- `python3 scripts/azoth-deploy.py --check`
- `python3 scripts/pipeline_lint.py`
- `python3 scripts/azoth_extract_product.py --validate-only`
- Focused pytest for touched release, roadmap, deploy, and extraction surfaces
- Full pytest only at release-candidate closeout or when release-surface changes justify it

### Product Extraction

Product extraction proves the public product tree is clean:

1. Extract into a temporary staging directory.
2. Confirm scaffold-only paths are absent.
3. Confirm configured sanitize patterns do not appear in extracted text files.
4. Confirm product `README.md` and public `.github/workflows/ci.yml` are generated.
5. Run product-side smoke checks from the extracted tree.

### Public Product Publishing

Publishing remains human-gated until a dedicated publish workflow is verified.

Recommended first public path:

1. Extract release candidate from `root-azoth`.
2. Sync extracted tree into a clean `azoth` checkout.
3. Run product CI/smoke checks.
4. Commit product update.
5. Tag `v0.2.0-rc.1` for the first release candidate.
6. Promote to final `v0.2.0` only after the operator accepts RC evidence.

Package-manager channels are explicitly out of scope for the first p4 rollout unless
the operator opens a separate release-distribution task.

## Personal Root Deployment

The personal root should be created from the published or release-candidate Azoth
product, not by turning `root-azoth` into the personal control plane.

The personal root should:

- install Azoth as a consumer project,
- keep personal knowledge and project inventory separate from toolkit source memory,
- connect to project repos through explicit handoff and project-state conventions,
- accept updates from public `azoth` releases or RC builds,
- remain safe to rebuild without losing personal state.

Open decisions for T-038:

- target repo/path for the personal root,
- private vs local-only storage policy,
- what belongs in global personal KB vs per-project KB,
- update cadence from `azoth` releases,
- first two real projects to onboard as pilot consumers.

## Post-p4 Continuation Model

p4 does not cancel unfinished initiatives. It deliberately keeps them out of the
rollout scope until the deployment loop is trustworthy.

After T-039 closes, unfinished initiatives resume from the initiative banks,
planning banks, inbox, and backlog surfaces through the normal Azoth route
decision path. The default rule is: choose the next initiative only after the
release/update path can carry new Azoth changes from `root-azoth` into public
`azoth`, then into the personal root, then into real project consumers.

The intended continuous-development loop is:

1. Develop Azoth changes in `root-azoth` under the current roadmap/initiative route.
2. Validate root truth with deploy parity, dashboard, lint, extraction validation,
   and focused tests.
3. Extract or sync a release-candidate product tree into `azoth`.
4. Run product-side CI/smoke checks and publish an RC or release after approval.
5. Update the personal root from the approved `azoth` release or RC.
6. Apply the updated personal root to real projects through explicit project
   handoff and project-state conventions.

This means future initiative work should become safer and more continuous, not
less ambitious. The freeze simply prevents unfinished feature threads from
becoming release blockers before the release machinery exists.

## Release Candidate Gates

p4 can close only when:

- p4 tasks T-034 through T-039 are complete or explicitly deferred with accepted risk,
- generated deploy parity is green,
- roadmap dashboard has no release-blocking drift warnings,
- installer-visible versioning matches the selected release policy,
- full product extraction and smoke tests pass,
- public publish path has either shipped an RC or has an approved blocker note,
- personal root deployment model is documented and either rehearsed or explicitly deferred,
- post-p4 continuation is explicitly routed back through initiative/backlog surfaces
  after the release/update loop exists,
- the final handoff names residual risks and the next concrete operator action.
