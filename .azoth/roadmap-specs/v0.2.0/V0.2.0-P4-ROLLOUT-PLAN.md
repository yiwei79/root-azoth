# v0.2.0-p4 Stabilization And Rollout Plan

Status: active milestone plan
Created: 2026-04-28
Roadmap version: v0.2.0-p4
Policy: freeze new initiative expansion until this phase closes

## Purpose

v0.2.0-p4 exists to turn the current Azoth work into something safe to use for
real projects. The phase is not a feature-growth phase. It is a stabilization,
release, and deployment-boundary phase.

The guiding decision is the hybrid operating model:

1. `root-azoth` remains the private development workshop and source of truth for
   toolkit evolution.
2. `azoth` becomes the clean public product repo produced by mechanical extraction.
3. The operator personal root becomes an installed Azoth deployment for personal
   project control, knowledge, and cross-project operation.

## Current Read

Autonomous-auto is complete for the shipped INI-AUTO-001 campaign, but the whole
repo is not release-clean yet. The release phase must preserve this distinction:

- Campaign truth: the autonomous loop can be Green and closed.
- Repo truth: generated mirrors, roadmap drift, installer versioning, product
  extraction, publish flow, and personal deployment still need release gates.
- Stable-release truth: the first stable release cannot claim full readiness until
  the complete test suite is green and the release evidence proves each shipped
  feature works as advertised.

As of the 2026-04-28 calibration pass, the autonomous-auto learning harvester is
real but bounded. It can automatically route safe internal self-heal work inside
an approved campaign budget; it must not be advertised as an unbounded daemon,
global self-modifier, or post-campaign continuation path.

Learning-system stabilization is therefore a release-readiness lane for p4, not
a new initiative. The first stable release may include narrow fixes that make the
advertised learning contract true: schema-valid captures, visible routing,
fail-closed protected stops, focused tests, and operator documentation. Broader
autonomous learning expansion remains deferred until after the release loop is
proven.

## First Stable Release Contract

The first stable release may claim:

- An operator can approve one bounded `autonomous-auto` campaign, then safe
  internal learning/self-heal signals can be captured, routed, opened, verified,
  and closed without the operator choosing every child step.
- The learning harvester reads repo-native campaign evidence and shows the
  selected learning route plus rejected alternatives in campaign reports.
- `strategy-preflight` consumes the learning-harvester recommendation before
  opening child work and preserves scope-gate, run-ledger, write-claim,
  lifecycle-route, protected-boundary, and fresh-approval checks.
- Protected, governed, M1, destructive, credential, network, cross-system,
  unclear-ownership, or user-governed improvements stop for human gate or
  inbox/intake instead of being auto-applied.

The first stable release must not claim:

- indefinite background self-improvement,
- automatic governance or instruction mutation without approval,
- automatic continuation after a completed Green campaign,
- release readiness while the full test suite, generated parity, extraction,
  product smoke, or release handoff evidence is red.

Release notes and operator docs must use this phrasing: supervised,
campaign-bounded autonomy. "No babysitting" means no per-child manual routing
inside an approved safe campaign; it does not mean no fresh approval, no gates,
or no protected-boundary stops.

## Freeze Rules

- Do not schedule new initiatives during v0.2.0-p4.
- Do not add new autonomy, memory, planning-bank, platform, or product feature
  work unless a release gate fails and the repair is the narrowest safe blocker fix.
- Learning-system fixes are allowed only as release-readiness repairs for the
  already-shipped campaign-bounded contract: inbox/schema validity, route
  evidence, strategy-preflight blocking, focused tests, and release docs.
- Keep new ideas in proposals, initiative banks, or inbox evidence until p4 closes.
- Prefer validation, packaging, publishing, documentation, and deployment-boundary work.
- Keep public product defaults smaller than root-azoth's development control plane.

## CI/CD Rollout

### Root Validation

Root validation proves the development workshop is internally coherent:

- `python3 scripts/azoth-deploy.py --check`
- `python3 scripts/pipeline_lint.py`
- `python3 scripts/azoth_extract_product.py --validate-only`
- Focused pytest for touched release, roadmap, deploy, and extraction surfaces
- Full pytest is mandatory before tagging any release candidate or final stable release

### Product Extraction

Product extraction proves the public product tree is clean:

1. Extract into a temporary staging directory.
2. Confirm scaffold-only paths are absent.
3. Confirm configured sanitize patterns do not appear in extracted text files.
4. Confirm product `README.md` and public `.github/workflows/ci.yml` are generated.
5. Run product-side smoke checks from the extracted tree.

### Public Product Publishing

Publishing remains human-gated until a dedicated publish workflow is verified.

Recommended first public path:

1. Extract release candidate from `root-azoth`.
2. Sync extracted tree into a clean `azoth` checkout.
3. Run product CI/smoke checks.
4. Commit product update.
5. Tag `v0.2.0-rc.1` for the first release candidate.
6. Promote to final `v0.2.0` only after the operator accepts RC evidence.

Package-manager channels are explicitly out of scope for the first p4 rollout unless
the operator opens a separate release-distribution task.

## Learning-System Stabilization Slice

The learning system is release-critical because first stable docs will mention
automatic learning/self-heal behavior. The acceptable p4 slice is narrow:

- Fix current release blockers in learning capture and inbox validation, including
  schema drift that prevents the full suite from passing.
- Prove the route chain from reflection or self-capture evidence to harvester
  classification, rejected alternatives, and strategy-preflight authority.
- Prove safe internal `auto_self_heal_now` routes can be applied inside an active
  approved campaign budget without per-child babysitting.
- Prove protected, cross-system, user-governed, unclear-ownership, destructive,
  credential, network, or M1/governance routes stop for human gate or inbox/intake.
- Prove completed Green campaigns do not create hidden continuation authority:
  new autonomous work still needs fresh approval.
- Update operator-facing docs and release notes so inbox/intake remains explicit:
  reflections sent to `.azoth/inbox/` are not silently auto-applied unless they are
  inside the safe campaign-bounded self-heal route.

Out of scope for first stable:

- automatic draining of `.azoth/inbox/`,
- automatic `$azoth-intake` decisions,
- automatic governance, prompt, skill, agent, or instruction mutation,
- background daemon-style self-improvement,
- cross-repo or personal-knowledge-base writes without explicit human approval.

## Personal Root Deployment

The personal root should be created from the published or release-candidate Azoth
product, not by turning `root-azoth` into the personal control plane.

T-038 documents the deployment boundary in
`.azoth/roadmap-specs/v0.2.0/PERSONAL-ROOT-DEPLOYMENT-MODEL.md`. The document is
design-only: it defines the three-plane model, knowledge boundaries, source
connections, update cadence, project onboarding flow, and live-install stop
conditions without creating a personal repository.

The personal root should:

- install Azoth as a consumer project,
- keep personal knowledge and project inventory separate from toolkit source memory,
- connect to project repos through explicit handoff and project-state conventions,
- accept updates from public `azoth` releases or RC builds,
- remain safe to rebuild without losing personal state.

Open decisions for T-038:

- target repo/path for the personal root,
- private vs local-only storage policy,
- what belongs in global personal KB vs per-project KB,
- update cadence from `azoth` releases,
- first two real projects to onboard as pilot consumers.

## Post-p4 Continuation Model

p4 does not cancel unfinished initiatives. It deliberately keeps them out of the
rollout scope until the deployment loop is trustworthy.

After T-039 closes, unfinished initiatives resume from the initiative banks,
planning banks, inbox, and backlog surfaces through the normal Azoth route
decision path. The default rule is: choose the next initiative only after the
release/update path can carry new Azoth changes from `root-azoth` into public
`azoth`, then into the personal root, then into real project consumers.

The intended continuous-development loop is:

1. Develop Azoth changes in `root-azoth` under the current roadmap/initiative route.
2. Validate root truth with deploy parity, dashboard, lint, extraction validation,
   and focused tests.
3. Extract or sync a release-candidate product tree into `azoth`.
4. Run product-side CI/smoke checks and publish an RC or release after approval.
5. Update the personal root from the approved `azoth` release or RC.
6. Apply the updated personal root to real projects through explicit project
   handoff and project-state conventions.

The final personal-control-plane deployment route now starts with a
cloud-native procedure slice before any new deployment writes:

1. **T-047 — procedure and desired state.** Define the declarative
   personal-root desired-state contract, reconciliation preflight,
   receipt/provenance fields, rollback reference, privacy/storage policy, and
   approval boundaries.
2. **T-048 — personal-root RC update rehearsal.** After T-047 and explicit
   operator approval, apply an approved `azoth` RC or release into the personal
   root from desired state and record a validation-backed receipt.
3. **T-049 — project onboarding pilot.** After the personal-root rehearsal,
   register one or two approved project consumers through pointer-only profiles
   and project-state handoffs; do not bypass project-local gates.
4. **T-050 — stable deployment closeout.** Close the personal-plane deployment
   by packaging evidence, documenting cadence, surfacing residual risks, and
   deciding whether private remote or encrypted backup is appropriate.

This route deliberately uses cloud-native operating discipline without assuming
an external cloud provider: declarative desired state, pull/reconcile thinking,
immutable revision evidence, explicit receipts, rollback, and small staged
applies. Release approval does not imply personal-root deployment approval, and
personal-root approval does not imply project-write approval.

This means future initiative work should become safer and more continuous, not
less ambitious. The freeze simply prevents unfinished feature threads from
becoming release blockers before the release machinery exists.

p4 can close only when:

- p4 tasks T-034 through T-039 are complete or explicitly deferred with accepted risk,
- generated deploy parity is green,
- roadmap dashboard has no release-blocking drift warnings,
- installer-visible versioning matches the selected release policy,
- the full root pytest suite is green,

  drift, planning-bank roadmap truth drift, repo-wide Ruff, Codex resolver
  contract drift, and any later full-suite regressions,

  `campaign-report` shows the learning route and rejected alternatives,
  `strategy-preflight` blocks protected/cross-system learning, and completed
  Green campaigns still require fresh approval before new work opens,
- learning captures and inbox reflections used as release evidence are
  schema-valid and deliberately routed; unresolved inbox/intake rows are named as
  blockers or deferred evidence, not silently treated as applied learning,
- focused learning-system tests prove safe self-heal application inside an
  approved campaign and fail-closed behavior for protected, cross-system,
  user-governed, or intake-owned improvements,
- operator-facing release notes state that autonomous learning is supervised and
  campaign-bounded, not global ungated self-modification,
- full product extraction and smoke tests pass,
- public publish path has either shipped an RC or has an approved blocker note,
- personal root deployment model is documented and either rehearsed or explicitly deferred,
- post-p4 continuation is explicitly routed back through initiative/backlog surfaces
  after the release/update loop exists,
- the final handoff names residual risks and the next concrete operator action.
