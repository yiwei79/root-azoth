# Azoth v0.3.0-rc.2 — outcome-centred proof surface

`v0.3.0-rc.2` is a release candidate for a clearer, evidence-led public
surface around Personal Harness OS. It does not retarget or alter the immutable
`v0.3.0-rc.1` tag.

The candidate makes the user problem and intended operating experience visible
before the framework vocabulary: complex work should retain its outcome across
research, discovery, specification, implementation, and evaluation, even when
those activities happen in separate agent threads.

## What changed

- Reframed the public README around outcome continuity: a thread is a bounded
  pulse of work, while durable goals, questions, decisions, evidence, artifacts,
  and evaluations form the continuity layer.
- Added a short path through the proof surface for readers who want the case
  study, executable contracts, or source evidence at different depths.
- Distinguished the broader outcome-graph direction from the routing, context,
  authority, and no-write rehearsal contracts implemented in this candidate.
- Made model evolution part of the architectural method: extra components and
  ceremony are falsifiable hypotheses that must earn and re-earn their place.
- Added an operator journey and implementation-status map to the Personal
  Harness documentation.
- Extended the case study with the concrete thread-drift failure mode, the
  outcome-centred response, and a more explicit simplification/evaluation loop.
- Removed release-version drift from generated README and public-validator
  assets by deriving their versioned references from the extracted manifest.

## Implemented proof retained

- Effect-aware routing through `HarnessRequest`, `HarnessDecision`, and
  `RouteCapsule`.
- Compact, source-referenced context assembly with raw-memory filtering and
  explicit missing-source warnings.
- A portable four-case rehearsal surface that checks route, authority, warning,
  and repository no-write expectations.
- Thirty focused public tests for the selected routing, context, rehearsal, and
  personal-knowledge contracts.

## Claim boundary

This candidate does not claim that the full outcome graph, autonomous
research-to-delivery pipeline, installer, cross-host parity, external adoption,
or production deployment of Azoth is complete. GloBuddy and SupplyOps are
production systems that shaped the method; they are not Azoth deployments.

## Validation evidence

The exact release-bearing extraction must pass:

- all 30 allowlisted portable public tests;
- the fail-closed public boundary validator;
- Ruff checks over the extracted public Python surface;
- privacy, credential-pattern, manifest, release-evidence, and local-reference
  validation; and
- a fresh no-write rehearsal against the extracted tree.

Exact source provenance is emitted into the extracted `azoth.yaml` manifest.
Publication remains gated on review of the complete extracted tree and explicit
human approval for the public commit, annotated tag, push, and prerelease.
